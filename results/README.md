本目录是 Agent 在**真实靶子** `ylinux_old-master` 上的两次运行产物，以及一份人工分析。

```

├── 人工分析报告.md                          逐条读解 11 条 finding（先读这份）
```

## 一、两次运行的出处

| | `fix-d` | `ctl-b` |
|---|---|---|
| `code_digest` | `e844a6d55780dc7e` | `a766d25a7b9c65de` |
| 与当前代码同指纹 | **是** | 否 |
| 模型 | `deepseek-v4-flash` | `deepseek-v4-flash` |
| `max_turns` | 50 | 40 |
| 产出 finding | 11 条（有效 10） | 6 条（有效 4） |
| 裁定分布 | `{NEEDS_HUMAN: 3, UNVERIFIED: 8}` | `{NEEDS_HUMAN: 2, UNVERIFIED: 4}` |

**`fix-d` 的 `code_digest` 与本仓库现在的代码完全一致**——这不是「时间上最后跑的那次」这种推断，是哈希相等。所以本仓库的代码**就是**产出 `fix-d` 的那份代码（45 个文件逐字节相同，哈希见 `../文件校验清单-GitHub包.json`）。同指纹的还有一次 `probe-trunc` 运行，它的账本用于结构判据，但报告本身未发布。

**`ctl-b` 的指纹不同，中间那批修复动了 7 个文件**（`agent/loop.py`、`agent/prompts.py`、`agent/registry.py`、`config.py`、`providers/base.py`、`providers/mock.py`、`report.py`）。因此：

> **这两行数字不可对照。** `ctl-b` 的 60% 召回**不能**用来论证「后来的改动让它退步了」——它们是两个不同工具的产物。这正是 `code_digest` 存在的理由（见 `../docs/01-设计思路.md` 第九节）。

两份报告的 `build.config` 里还记着预算、阈值、开关等运行参数，可以与代码哈希分开核对。

## 二、发布前对这 4 个文件做了什么

发布的是**脱敏后的报告**。原始产物含被审代码片段与靶子自带的凭据，按本项目自己的交付约定不外发（该约定来自一次真实事故：账本混进过交付包，文件清单从 61 条跳到 145 条）。

脱敏分两层，实现在 `_build_github_package.py`（**该脚本不在本仓库内**）：

| 层 | 做什么 |
|---|---|
| 引擎自带 | `engine/redact.py` 的 `scrub()`：令牌/私钥/连接串等模式，值换为「前 3 字符 + 长度 + 指纹」 |
| 发布侧补的三条 | R2 凭据词所在行的引号字面量全遮（不限长度，命中 551 处）；R3b 同行裸数字串（7 处）；R4 本机标识（用户名、绝对路径，4 处） |

**为什么发布侧要补**：`redact.py` 的 `assigned_secret` 规则要求引号内 **≥8 字符**，而靶子里的库口令是 **6 位**，整条规则不命中，原文进了 finding 标题。这是本次交付中发现的真实缺陷，记在 `../docs/03-问题与取舍.md` 第 1 条。**没有修改 `engine/redact.py`**——它参与 `code_digest` 计算，改它会让所有已归档运行与当前代码失去可比性。

**验证到什么程度**：发布自检用了**与脱敏规则无关**的具体事实做硬断言（靶子库口令原文、用户名、Windows 用户目录前缀、各类令牌形态、私钥块、带密码连接串），全部为 0；另做了一次独立扫描，把靶子全部 `.py` 里**出现在凭据关键词所在行、且形态像「值」而非标识符**的 29 个引号字面量逐个比对，**没有一个出现在这 4 个文件里**。

那次硬断言还**拦下过我一次**：`docs/03` 的初稿为了演示 `grep` 把靶子口令原文写进了正文，自检报「六位口令原文=3」。已改成用模式查找。详见 `../docs/03-问题与取舍.md` 第 1 条末尾。

即便如此：**这仍不构成「保证无敏感数据」**。正则扫不全，`engine/redact.py` 自己的注释就写着「它不保证扫全（没有任何正则能）」；而且上面那次扫描证明的是「这些已知的值不在里面」，不是「脱敏把每一个都拦下了」。

## 四、怎么用这些数字

```bash
cd ..                       # 回到仓库根
python -I tests/score.py results/fix-d
python -I tests/score.py results/ctl-b
```

评分器读的就是本目录里**已脱敏**的那份 JSON，所以你跑出来的四个维度数字应当与 `../docs/02-准确性如何验证.md` 第三节的表一致。

**读之前请先知道**：`fix-d` 的召回被评分口径**低估**（V11 被漏计，实际不低于 60%），「误报 1 项」被**高估**（实际为 0）。两个缺陷方向相反、都在 `score.py:_match()` 里，**都没有修**——由被评者在交付前把自己的评分改高是最不该做的动作。机理见 `../docs/02` 第四节。

真正该先读的是 `人工分析报告.md`：它逐条核对了 11 条 finding 在靶子源码里的原文，并写明每条残余的不确定性。
