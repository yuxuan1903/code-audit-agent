# 如何确认 Agent 输出结果的准确性

结论先说：**这份工具的输出没有被「确认」过，只被「量化」过，并且量化本身有一个已确认的缺陷。** 下面把这句话拆开。

---

## 一、两种「验证」必须分开，因为它们不可互证

要回答的问题其实是两个：

| | 问题 | 尺子 |
|---|---|---|
| **结构** | 它真的是「模型自主决定调什么工具」吗？闭环真的自动串起来了吗？ | `tests/_check_requirements.py` |
| **效果** | 它报出来的东西对不对？该报的报了吗？ | `tests/score.py` |

`_check_requirements.py` 的开头写明了为什么不能混：

> ——而验收报告里曾经用**效果指标**（召回率、误报数、收口次数）去回答它们。
> 那是两把尺子量错对象：效果差可以是"机制成立、效果不好"，机制不成立才是没满足要求。
> 反过来，一个固定顺序的脚本串联也能跑出高召回。**两者不可互证。**

所以这份脚本**只测结构，不测效果**，六条判据每条都写明「它为什么能证伪」：

| 判据 | 内容 | 为什么能证伪 |
|---|---|---|
| A | 跨运行的调用序列**不相同** | 脚本串联 ⇒ 序列必然逐字重复；相同即证伪 |
| B | 工具失败后**改变做法** | 「自主」的定义：脚本收到错误只会原样重试 |
| C | 工具面**真实约束** | 未注册的工具名也被接受 ⇒ 「调用工具」只是装饰 |
| D | 链路**完整**（五阶段产物齐备） | 缺环或人工断点即证伪 |
| E | 结论**落盘**且真的写进产物 | 只在内存里给结论 = 没闭环 |
| F | 收口**由账本判定** | 候选未处置完却 `concluded` ⇒ 收口是宣布的，不是判定的 |

判据 A 需要**两个**运行目录——单次运行的序列不与任何东西可比，「是否重复」这个问题在单次运行上无意义。这不是缺陷，是这类判据的固有性质。

### 实测读数

用同一构建指纹（`e844a6d55780dc7e`）的两次真实运行作对照，六条判据全部通过：

```
待判运行 2 个，构建指纹 ['e844a6d55780dc7e']

要求 1 —— 真正的 Tool Calling 结构（谁在决定）
  ✅ A 跨运行序列不相同（脚本串联会逐字重复）
      可比的运行对 1 组，相似度 30.0%–30.0%。
      其中**同构建**那一对是 30.0%——这一对不受构建差异干扰，是本判据最干净的证据。
  ✅ B 工具失败后**改变做法**（脚本只会原样重试）
      失败 2 次：换工具 0 次、同工具换参数 2 次、原样重试 0 次。
        fix-d 第 18 轮：list_candidates 参数被拒 → 重发时换了参数
        probe-trunc 第 24 轮：read_code 参数被拒 → 重发时换了参数
  ✅ C 产物中零 `unknown_tool`（模型从未调通不存在的工具）
  ✅ C 注册表直接探针：未注册的工具名被拒 / 必填参数缺失被拒

要求 2 —— 完整闭环（是否自动串联）
  ✅ D 链路完整：引擎 → 候选 → Agent → 账本 → 报告，五环齐备
  ✅ E 至少一次到达最终结论，且结论**真的写进产物**（fix-d：summary=有，limitations=7）
  ✅ F 收口由账本判定：fix-d concluded，未处置候选=0，覆盖完成=True

✅ 所有硬性判据通过
```

三条值得单独看：

- **判据 A 的读数是「相似度 30%」而不是「不同」**——脚本串联的相似度会是 100%。这个数字同时说明两次运行确实各走各的路，且它们是在同一份代码上（同指纹）跑的，排除了「差异来自代码变化」这个混淆。
- **判据 B 的关键不是「失败了几次」，是失败之后做了什么**：0 次原样重试、2 次同工具换参数（模型修正自己）。脚本收到错误只会原样重试。
- **判据 F 把两次运行分开对待**：`fix-d` 是 `concluded` 且未处置候选为 0（通过），`probe-trunc` 是 `budget_exhausted` 且挂着 31 条未处置候选——它不算通过，也不算失败，因为**它本来就没说自己审完了**。把「如实报告预算耗尽」与「宣称审完了」区分开，是这条判据存在的全部意义。

> ⚠️ **可复现性限制**：这三条判据读的是 `ledger.json`，而运行账本按项目自己的交付约定**不随仓库发布**（账本含被审代码片段与凭据字符串）。所以第三方无法用本仓库里的文件重跑这一段——它能重跑的是上一节的四维评分（那部分只依赖已发布的报告）。这是本次交付的一个真实缺口，不是疏忽：发布账本与不泄露被审源码片段，两者只能选一个。

## 二、效果怎么量：人工真值 + 四维评分

`tests/ground_truth/ylinux.json` 是人工写的清单，两类：

**8 条「必须报出」**（V1–V12 的子集）。其中 **3 条带 `optional` 标记**（V3 `XMLRPC_DEBUG=True`、V4 `XMLRPC_METHODS` 暴露写接口、V12 XML-RPC 端点 `csrf_exempt`），`score.py:270/294` 把它们**排除出召回分母**，所以召回率的分母是 **8 − 3 = 5**，Q1 表里出现的是 `x/5` 与随行的「（可选 x/3）」。下表列的是进分母的那 5 条中的 4 条：

| id | 位置 | 内容 |
|---|---|---|
| V1 | `settings.py:18` | 生产配置 `DEBUG=True` |
| V2 | `settings.py:79` | 硬编码 `SECRET_KEY`（会话签名密钥） |
| V9 | `lib/ylinux_xmlrpc.py:60` | `delete_all_topic` **只认证不鉴权** |
| V10 | `lib/ylinux_xmlrpc.py:105` | 文件名未做 basename 净化 → 可写 `.html` 存储型 XSS |
| V11 | `app/account/views.py:38` | `?next=` 未校验 → 开放重定向 |

**6 条「必须不报」**，全是刻意设计的陷阱，用来区分「真的推理过」与「模式匹配」：

| id | 陷阱类型 |
|---|---|
| S1 / S2 | `bandit` B608 SQL 注入误报——需要数据流推理才能确认拼进去的是 `qn()` 引用字面量而非用户输入 |
| S3 | `os.system` 的参数来自 `os.popen('whoami')`——需要确认命令是常量 |
| S4 | `AnonymousUser` 权限分支**正确返回 False**——报了就是误报 |
| A1 / A4 | 内嵌第三方库的缺陷——**报出不算错，归因成项目问题才算错** |

**评分分四个维度，刻意不合成一个总分**：

```
召回率　误报数　归因正确　边界声明
```

理由见 `score.py` 自己的提示：**「召回高但误报多 = 模式匹配；召回低但误报零 = 过于保守。」** 合成一个分数会把这两种截然不同的失败模式掩盖成同一个数字，而它们对应的改法完全相反。

真值清单本身也是人写的判断，不是绝对真理——它衡量的是「与本项目既有认知的一致程度」。这句话写在评分器的输出里，我不想把它藏起来。

## 四、评分器本身有两个已确认的缺陷，方向相反

两个缺陷都在同一个函数 `score.py:_match()` 里：一个让召回被**低估**，一个让误报被**高估**。它们不是「调参偏好」问题，而是会各自独立改变结论的口径错误。

### 4.1 缺陷一：召回被低估（`fix-d` 的 V11）

`fix-d` 被记为漏报的三条里，**V11 是评分口径造成的漏计**，不是 Agent 没看见。

证据链：

1. 真值 V11 的锚点是 `app/account/views.py:38`，标题「登录/登出 next 参数未校验导致开放重定向」，类别 `open_redirect`。
2. `fix-d` 的报告里**确实有一条**开放重定向 finding：`F-007`（`open_redirect` / CWE-601），它的「证据」一节逐字写着：

   > `app/admin/views.py:62 与 app/account/views.py:38 —— HttpResponseRedirect(request.session.get('previous_url'|'login_redirect_url','/'))`

3. 但 `score.py` 的 `_match()` 第一道就是**硬文件门**：

   ```python
   if (loc.get("file") or "").replace("\\", "/") != item["file"].replace("\\", "/"):
       return False
   ```

   `F-007` 把 `admin/views.py` 的多处（62/134/192/257/354）与 `account/views.py:38` 合并成一条，主位置记在 `app/admin/views.py:134`；V11 的锚点在 `app/account/views.py` ⇒ 文件不等 ⇒ 直接返回 `False`，**后面的兜底根本不会执行**。

4. 而那条兜底存在的理由，`score.py:86-89` 的注释写得很清楚：

   > 这条是为「Agent 把多个问题合并成一条」准备的——合并本身会丢信息（少了「哪个方法无鉴权」这个最关键的区分），但其中的每一项确实被看到了，**不该算漏报**。

> **⚠️ 归因修正。** 我最初把这里写成「评分器的行为与它自己声明的意图相矛盾」，**这是错的**。真值基准 `tests/ground_truth/ylinux.json` 的 `scoring.match` 写的是：「文件路径精确 + 行号落在 `[line, line+window]` 区间内；或 category 关键词命中**且文件相同**」——**两个分支都要求文件相同**。所以 `score.py:68` 的文件门是**基准要求的**，实现忠于基准。
>
> 真正的矛盾在另一处：**兜底的注释承诺它处理「合并成一条」，而基准规则只允许它处理「合并且没换文件」的合并**——兜底的实际作用域是「同文件、行号漂移到窗口外」，跨文件合并它管不了。而跨文件恰恰是合并的常态（同文件的话主位置本来就对得上，多数时候不需要兜底）。
>
> **这个修正改变了修法**：要修不能只动 `_match()`，得动**基准的匹配规则**（允许跨文件的关键词匹配）。那是一个比「修 bug」大得多的动作，也让「交付前不修」这个决定更站得住。

**本次交付没有修改评分器。** 修好它会让召回从 40% 变成 60%，而由**被评者自己**在交付前顺手改高评分，是最不该做的动作。缺陷在这里写明，数字按原样发布。

所以准确的说法是：**这套工具的召回率按当前评分口径是 40%，其中至少一条（V11）属于口径漏计，真实召回不低于 60%——但「不低于」是有依据的下界，不是一个新的结论。**

### 4.2 缺陷二：误报被高估（`fix-d` 的 S4）

`fix-d` 那条「误报 1 项」**不是真的误报**。

真值 S4 的锚点是 `app/account/models.py:310`（内容：`AnonymousUser` 权限分支**正确返回 False**，报了才算误报），窗口 40 ⇒ 命中区间 **[310, 350]**。

`fix-d` 在该文件里只有一条 finding：`F-006`（`weak_crypto`，内容是口令盐用非密码学 PRNG 且盐仅 5 位十六进制），它的位置是：

```json
{"file": "app/account/models.py", "line": 232, "end_line": 430,
 "function": "User.set_password / RegisterManager.create_profile / ..."}
```

`_match()` 的最后一个子句是：

```python
if lo <= line <= hi or (line <= hi and end >= lo):
    return True
```

代入：`232 <= 350` 且 `430 >= 310` ⇒ **成立**。于是一条关于**随机数盐**的 finding，因为它的行区间恰好横跨了 S4 的窗口，被算成了「误报了 `AnonymousUser` 权限分支」。

注意这里与 4.1 的**不对称**：基准的 `scoring.match` 只说「行号落在 `[line, line+window]` 区间内」，**从未授权行区间重叠也算命中**。`or (line <= hi and end >= lo)` 是实现自行加宽的口径。

| | 与基准的关系 |
|---|---|
| 4.1（召回被低估） | 实现**忠于**基准，冲突在基准规则与兜底注释之间 |
| 4.2（误报被高估） | 实现**超出了**基准——基准没给这个子句授权 |

**成因是唯一的**：六个陷阱条目的 `categories` 与 `keywords` **全都是 `None`**（见 `tests/ground_truth/ylinux.json`），也就是说陷阱只能靠「文件 + 行窗口」匹配，没有第二道判别。行区间一重叠，就无法区分「它报的是不是这个陷阱」。

**后果**：

1. `fix-d` 在这套真值集上的真实误报数是 **0**，不是 1。
2. 第三节里 `fix-d`（40% / 1 误报）与 `ctl-b`（60% / 0 误报）的对照，**失去了它最自然的那个读法**——「新版更激进所以误报更多」。那个读法从来就没有依据：`ctl-b` 之所以是 0，只是因为它在该文件里没有一条横跨该窗口的 finding，而不是因为它更克制。**两次运行在误报轴上的差异，完全由这一条子句产生，与模型行为无关。**
3. 行区间匹配本身**有正当理由，而且我核过了**：F-006 的位置确实是 `232–430`，跨 4 个函数（`User.set_password` / `RegisterManager.create_profile` / `User.reset_activation_key` / `UserManager.make_random_password`，`function` 字段自己列了出来）。同一个模式在 4 处重复出现，**而位置模型只能记「一个区间」**——用单个行号表示它才是不准确的。所以修法不是「删掉这个子句」，而是「吸收之前必须先做主题判别」。而陷阱条目不带类别/关键词，**真值集本身也提供不了这个判别依据**。
4. 顺着第 3 点往下看，这里暴露的是**位置模型的建模局限**，不只是评分器的毛病：一条 finding 只能有一个 `location`，于是「4 处同类问题」被压成一个 198 行的区间，而这个区间又去撞了别人的陷阱。同一局限在 `fix-d` 里还有第二处表现——F-007 的位置字段是 `{"line": 134, "end_line": 62}`，**区间倒置**（`end_line < line`），该条 finding 的重叠匹配因此被静默禁用（它没被文件门拦掉的话就是另一种结果）。见 `results/人工分析报告.md` §3.3。

第 3 点指向一个比评分器更深的问题：**这六个陷阱是用「位置」定义的，所以同文件里任何一条跨度较大的 finding 都可能"碰到"它们。** 要让陷阱真正只惩罚它想惩罚的行为，真值需要携带**负向主张**（「不许声称 X」），而不只是一个坐标。这是真值集的设计问题，不是 matcher 的实现问题。

## 五、另一条是真漏报，判据同样具体

同一次运行里的 V1（`settings.py:18` `DEBUG=True`）**是真漏报**，判据：

```bash
grep -oE "DEBUG\s*=\s*True" results/fix-d/audit-report.md    # → 1 处
```

这一处出现在**推理轨迹**里（`DEBUG=True → C4 finding (debug en...`）——模型看见了、在推理里提了一句，但**从未把它记成 finding**，也没进候选清单。`fix-d` 的 C4 类 finding（F-008）只写了 `SECRET_KEY` 与数据库口令，不含 `DEBUG`。

这正是 `docs/01` 第六节「对账线索」要治的失败模式，而它这次没能兜住。写在这里是因为：**一个机制的价值取决于它在真实失败面前的表现，而不是它的设计文档。**

## 六、测试结果本身也要防止「读错」

`tests/` 里的断言脚本大多有 `sys.exit()`，退出码可直接用。但有一个反例：

**`tests/_t_agent.py` 末尾没有 `sys.exit()`，它的退出码恒为 0，不能拿来当通过证据。** 它的通过证据是模块级计数器 `e_bad`（604 定义 → 610 由 `echeck` 自增 → 1111 判定）。交付实测的输出末行是：

```
  ✅ 收敛对账四项动作齐备（提得出来 / 认账不重复 / 有出口 / 写得进报告）
```

这正是 `if not e_bad` 那一支 —— `e_bad == 0` 是**直接观察到的**，不是从退出码推断的。

同理，这份脚本输出里会出现 `❌`，**不等于失败**：本次 142 项 `✅` / 2 项 `❌`，那 2 项是被**故意拒绝**的工具调用标记（`record_finding` 缺字段、`conclude` 被 blocker 拦住），每个后面都紧跟一条 `✅` 确认「拒绝得对」。把 `❌` 的条数当成失败数会得到完全相反的结论。
