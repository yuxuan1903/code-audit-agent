# 主要问题与取舍

## 第一部分：主要问题

### 1. 运行时脱敏放过短口令，导致报告自称「不含凭据明文」不成立

**这是本次交付过程中发现并修掉的一个真实缺陷。**

`fix-d` 的报告里有一节写着：

> **凭据扫描的特别说明**：……本报告不包含任何凭据明文，清单见附录的「凭据清单」一节。

这句话**不成立**。实测：

```bash
# 用「六位纯数字的引号字面量」这个模式去找，而不是把那个值写在这里
grep -oE "'[0-9]{6}'" results/fix-d/audit-report.md   # → 7 处
grep -oE "'[0-9]{6}'" results/fix-d/audit-report.json # → 12 处
```

它出现在 finding 标题里（`F-008：settings.py 硬编码 SECRET_KEY 与数据库口令（'……'）`），也出现在模型的推理轨迹里。

**根因**在 `engine/redact.py` 的 `assigned_secret` 规则：

```python
r"(?i)\b(?:password|passwd|pwd|secret|...)\b\s*[:=]\s*(['\"])([^'\"\n]{8,})\1"
```

引号内要求 **≥8** 字符，而被审代码里那个口令是 **6 位**——整条规则不命中。运行时放过短口令其实是**合理权衡**（遮得太狠会淹掉真信号，也会让模型对不上自己刚读到的行），问题不在规则本身，而在于**报告据此声称了一个它保证不了的性质**。

**处置**：发布侧在 `scrub()` 之上补三条过遮规则（实现在打包脚本 `_build_github_package.py` 里，**该脚本不在本仓库内**）：

| 规则 | 内容 | 本次命中 |
|---|---|---|
| R2 | 凭据词所在行的**引号字面量全遮**（不限长度） | 551 处 |
| R3 | 引号内 **6 位以上纯数字**全遮 | 0 处（R2 已覆盖） |
| R3b | 凭据词所在行的**裸数字串**全遮（覆盖不带引号的写法） | 7 处 |
| R4 | 本机标识（用户名、绝对路径）替换为占位符 | 4 处 |
| R1 | 项目自己的 `scrub()` | 8 行 |

**没有修改 `engine/redact.py` 本身**——它参与 `code_digest` 计算，改它会让已归档的所有运行与当前代码不再可比。这是一个有意的取舍：**宁可发布侧多一层，也不动指纹覆盖的代码**。

**留下的教训**：脱敏的断言不能由脱敏自己来证。发布自检里的「硬断言」刻意用与脱敏规则**无关**的具体事实（那个六位口令串本身、用户名、Windows 用户目录前缀、AWS/Anthropic/GitHub 令牌形态、私钥块、带密码连接串）——用同一套正则自证等于自说自话。即便如此，它仍**不构成「保证无敏感数据」**：没有任何正则能保证扫全，这是 `redact.py` 自己就写明的边界。

**⚠️ 这个断言在交付前拦下了我自己。** 这一节的初稿里，我把靶子那个六位口令**原文写进了本文档**——为了演示 `grep` 怎么找出它。发布自检报「六位口令原文=3」，指向的正是本节。我改成了用模式去找（`grep -oE "'[0-9]{6}'"`），文档里不再出现那个值。

这件事值得单独记：**我在写「不要转述凭据」这一节的过程里转述了凭据。** 发现它的不是我的自省，是一条与脱敏规则无关的硬断言。这说明断言的价值恰恰在于它**不懂上下文**——如果它「聪明」到能判断「这里是在举例，不算泄露」，它就会漏掉真正的泄露。

同一轮自检还报了 3 处「Windows 用户目录前缀」这个**模式名本身**——那些是提及、不是泄露。我改的是散文（改写成「Windows 用户目录前缀」这样的说法），**没有放宽断言**：真泄露与提及在字面上长得一样，为迁就自己的措辞而放宽断言，就是上面那句「用同一套正则自证」的变体。

### 2. 静默降级：把「找不到东西」伪装成「东西是空的」

第一代原型被移入子目录后，靶子留在了上一级，于是 9 个测试脚本里写死的路径全部指空。表现不是报错，而是：

| 脚本 | 当时的输出 | 真实的含义 |
|---|---|---|
| `_t_collect.py` | 「入口契约核验：**0/22** 通过」，22 项全红 | 范围为空 |
| `_t_engines.py` | 「候选 C0001 不存在」 | 引擎候选为空 |
| `_t_agent.py` | `IndexError: list index out of range` | 对账线索为空 |
| `_tune_recall.py` | **退出码 0**，打一张空表 | 账本目录不存在 |

**这四处都不是审计逻辑的缺陷**，但它们暴露了一个真实的设计问题：**把「找不到靶子」静默地当成「靶子里什么都没有」，会让一整屏判据红掉，而红的原因与被审代码毫无关系。** 最后一行更糟——它把「找不到账本」印成了「账本里什么都没有」，退出码还是 0。

**处置**：

- 新增 `tests/_target.py`：定位被审仓库，**找不到就明确退出（码 2）并打印用法**，附上环境变量 `AUDIT_TARGET` 作为显式指定；9 个脚本改为调用它。
- `tests/_tune_recall.py` 改为**必须显式给出账本目录**，否则打印用法并退出 2。

**为什么定位工具放在 `tests/` 而不是 `engine/util.py`**：`build_fingerprint()` 用 `engine/**/*.py` + `audit.py` 算 `code_digest`，往 `engine/` 里加一个函数会让已归档的十余次真实运行与当前代码不再可比。测试不参与指纹计算（「改了测试不该让两份报告失去可比性」），所以放 `tests/`。**这条约束直接决定了实现位置**，不是随手放的。

**代价**：改动只限于测试脚本的定位方式与提示语，**审计逻辑一行未动**；`engine/` 逐字节未改，指纹不变（`e844a6d55780dc7e`，与 `fix-d` 运行记录的指纹一致）。

### 3. 「提到了但没落账」是最难治的漏损

两种表现，都是真实的：

- **`fix-d` 的 V1**：`DEBUG=True` 在推理轨迹里出现过一次，**从未变成 finding**。这是真漏报（判据见 `docs/02` 第五节）。
- **`real-reap` 的 V10**：第 37 轮推理提到了正确的净化点，但线索配额已在第 32 轮用尽，这条提及永远没变成线索。而用掉的那 6 条配额里 **5 条最终被系统自动回收**——等于烧在了「再等两轮它自己就落账了」的位置上。

`recall.py` 这个机制就是为它写的，而它**没有兜住 V1**。原因不是判据不准：`tests/_probe_recall.py` 在四份真实账本上的回放显示扫描器能捞到目标位置。问题在**时机与配额**——真实运行里配额会在中途被占满，而重放实验里每条提及都从空账本出发，所以重放**系统性高估**了捞取能力。

`tests/_tune_recall.py` 的文档把这件事写得比我能写的更清楚：

> 调参时可以把这张表当作"配额不至于让某条提及永远进不来"的下界证据，**但不能拿它当作"改了配额语义就能捞到 V10"的证明**——那个只能由真实运行回答。

### 4. 效果数字不能直接读——评分器给了两个方向相反的错

| | 召回 | 误报 |
|---|---|---|
| `fix-d`（当前代码） | 40%（**被低估**，下界 60%） | 1 项（**被高估**，实际 0） |
| `ctl-b`（旧版代码） | 60% | 0 |

**先说不能下的两个结论**：

- 不能说「新版退步了」——两次运行 `code_digest` 不同，中间那批修复动了 7 个文件，它们是两个不同工具的产物。
- 也不能说「新版改进了」——`fix-d` 的 finding 更多（11 条 vs 6 条）、覆盖更细，但在这个真值集上召回更低。

诚实的表述是：**在一个靶子、两次非同指纹运行上，无法对这两版代码的优劣下结论。** 要下结论需要同指纹的对照运行，本次交付没有做。

**更值得记的是这张表本身**：两个数字都被评分器改变了方向——召回被压低（V11 被漏计），误报被抬高（S4 是行区间重叠的产物）。机理与证据见 `docs/02` 第四节。两个缺陷在同一个函数 `score.py:_match()` 里：一个是文件硬门排在兜底之前（该匹配的不匹配），一个是行区间重叠子句过宽（不该匹配的匹配）。

**这条经验比那两个数字值钱**：在一个效果指标上，**测量工具和被测对象一样需要被验证**。我第一次读这两个数字时是照单全收的——40% 与 1 项误报都在我自己的会话里被引用过，直到为了写这份文档去追「为什么报了开放重定向却算漏报」，才发现两个方向的错误都存在。一个只盯着「模型表现如何」的验收流程，会把测量口径的错误长期当成模型的能力问题。

**修了吗？没有。** 修好它们会让召回从 40% 变成 60%、误报从 1 变成 0——由被评者在交付前动手把自己的评分改高，是最不该做的动作。缺陷写在 `docs/02` 里，数字按原样发布。

一个附带的观察，**我先写错、后来核对时才改对**：我起初写的是「三条 HIGH/CRITICAL 全部退回 `NEEDS_HUMAN`…与 `docs/01` 第二节的设计意图吻合」。核对后发现**不吻合**——那三条的 `NEEDS_HUMAN` 全部来自「验证者未在预算内提交结论」的引擎兜底，不是验证者的判断（见下面第 7 条）。只有「这三条走了对抗验证」这一半是真的（与 `require_adversarial_for: [CRITICAL, HIGH]` 一致，是真实行为）。

**这两次自我更正有一个共同点值得记**：40% / 1 项误报这两个数字，与「三条 HIGH/CRITICAL 被验证者退回人工」这句话，**都是我在自己的会话里先当成事实引用、后来为了写文档去追证据才发现不对的**。错误不在数据里，在我读数据的方式里——**照单全收一个看起来合理的叙述**。一个只盯着「模型表现如何」的验收流程，会把这些口径问题长期记成模型的能力问题。

### 5. 指纹不覆盖「实际用哪个端点」，而模型名其实记着

**这一条我最初写错了，是被自己的核查推翻的。**

我原先写的是「模型名没有记进报告，事后无法从产物中核实」。为了写 README 的「依赖哪些模型」去查产物时，我先这么下了结论；后来真去读 JSON 才发现**记着**：

```json
"build": {"config": {..."provider": "auto", "model": "deepseek-v4-flash",
                     "max_output_tokens": 8192, "max_turns": 50, ...}}
```

而且报告正文里也印了模型名（`fix-d` 的 md 出现 3 处、`ctl-b` 4 处）。

**真正的缺口是另一件事**：`config` 里存的是**配置值** `"provider": "auto"`，不是 `--provider auto` **解析之后的结果**；`base_url` 同样不在产物里。所以「同一个模型名、换了一个兼容端点」这种变化，指纹和产物都看不出来——而这恰恰是最容易悄悄发生的一项变化（`docs/01` 第九节说指纹的设计目标就是让「两次运行可比」成为可核事实，模型与端点都属于「不覆盖」的盲区，只是程度不同）。

**两次运行的 `config` 差异是**：`max_turns`（50 vs 40）与 `max_output_tokens`——这两个值不同这件事是**可核的**，正说明这套记录在它覆盖到的范围内是好用的。

**教训与这一条本身同等重要**：我在同一份文档里同时犯了「没核实就下结论」（本条）与「拿一个合理叙述当事实」（第 4 条）两种错。它们的共同解药只有一个——**发布前把每条要写进文档的断言回去核一遍**，而不是复述自己上一次说过的话。

### 6. 预算与上下文

`fix-d` 的运行是 **50 轮 / 86,323 tokens / 604 秒**，上下文压缩 **11 次**。同指纹的 `probe-trunc` 则是 `budget_exhausted` 终止，**挂着 31 条未处置候选**。

这两条路径反映了设计的两个面：一边是「跑完了、收口了、候选清零」，另一边是「预算烧完、如实报告没跑完」。后者不做成失败，是有意的——`_check_requirements.py` 的判据 F 只要求 `concluded` 的运行候选清零，**不要求所有运行都 concluded**。把「如实说没做完」和「宣称做完了」区分开，比逼着它两种都说成一种更有价值。

### 7. 对抗验证没跑完，被摘要读成了「验证者的判断」

**这是本次交付里后果最重的一个问题**，因为那些是 HIGH/CRITICAL 条目。

**事实**（机械核对，可复现）：

| 运行 | `NEEDS_HUMAN` 条数 | 其中来自兜底 | 验证者真正提交的 |
|---|---|---|---|
| `fix-d` | 3 | **3** | 0 |
| `ctl-b` | 2 | **2** | 0 |
| 合计 | **5** | **5（100%）** | **0** |

三条 `NEEDS_HUMAN` 的 `reasoning` 字段原文都是同一句：**「验证者未在预算内提交结论。」** `rebuttal` 也是同一句「无法自动核实，需人工复核。」，`sanitizers_checked` 是空列表。这来自 `engine/agent/verify.py:235-239`：

```python
if not d:                                    # 验证者没提交
    return VerificationOutcome(fid, Verdict.NEEDS_HUMAN,
                               "验证者未在预算内提交结论。",
                               "无法自动核实，需人工复核。",
                               [], chash, turns, tool_calls)
```

验证者每条的预算是 **8 轮**（`verify_finding(..., max_turns: int = 8)`，由主 Agent 在 `adversarial_verify` 工具调用里给，默认 8）。

**兜底本身是对的**，这点要说清楚：验证者没提交时，既不能算 `CONFIRMED`（没被证实），也不能算 `FALSE_POSITIVE`（没被证伪），把它送进人工队列是**安全的方向**。错的是**同一个裁定值同时承担了两种含义**，于是下游有三处替验证者说了它没说过的话：

| 位置 | 说了什么 | 为什么不成立 |
|---|---|---|
| `report.py:230-233`（摘要） | 「**是验证者把判断退回给了人**」 | 验证者没有「退回」，它没跑完 |
| `verify.py:271-272`（给 Agent 的工具回执） | 「🟡 **静态无法判定**，需人工复核：…」 | 原因是轮数用尽，不是判定为静态不可解 |
| `docs/01` 第二节（我写的设计文档） | 把 `NEEDS_HUMAN` 讲成「鉴权取决于网关配置」这类判断 | 同上 |

而且**这个误读会传染**：`fix-d` 报告第 38 轮的 Agent 轨迹里出现了这样一句自述——

> Interesting: the verifier ran out of budget (static undecidable → needs human).

它把引擎给的那句「静态无法判定」照单全收，与自己观察到的「ran out of budget」并列写在一起。**引擎的标签塑造了 Agent 自己的结论**，而这句话又被写进了报告。

**为什么没修**：`report.py` 与 `verify.py` 都在 `engine/**` 里，参与 `code_digest` 计算。改它们，`fix-d` 记录的指纹就不再等于当前代码——而「这份代码就是产出这份报告的那份代码」是整个交付的证据基础（见取舍表第 11 项）。所以与第 1 条同样处理：**问题写在文档里，代码一行不动**。

**正确做法**（留给下一代）：兜底必须产生**可分辨的值**——比如新增 `VERIFIER_INCOMPLETE`，或让 `stage` 字段区分 `adversarial` 与 `adversarial_incomplete`。这不是词表变大，而是**让「没跑完」和「跑完了但定不了」在数据层就分开**；在这之前，任何按裁定值做的统计（包括报告的摘要、门禁的判定、评分器的分母）都会把两者混为一谈。

**它对交付的影响在这份文档之外**：`results/人工分析报告.md` 里那三条 HIGH/CRITICAL 的「验证」栏全部是空的，我改用逐条回源码核对补了这一课。也就是说，**这三条的安全网一直只有人工**，而报告摘要让它看起来有两层。

### 8. 行尾被 Git 改写，会把「这份代码就是产出那份报告的那份代码」变成假话

**这是发布前自检抓到的第二个真实缺陷**，而且它不会以任何报错的形式出现。

事实是这样的：本交付件里有 **7 个文件本来就是 CRLF**——

| 文件 | 为什么参与不了「统一成 LF」这件事 |
|---|---|
| `engine/providers/anthropic_compat.py`、`base.py`、`openai_compat.py` | **在 `code_digest` 的计算范围内**（`engine/**/*.py`） |
| `results/{fix-d,ctl-b}/audit-report.{md,json}` | 由发布脚本在 Windows 上写出，Python 的 `write_text` 按平台把 `\n` 落成了 `\r\n` |

而 `code_digest` 是对**文件字节**算的（`engine/util.py:192` 的 `read_bytes()`）。Windows 版 Git 的默认 `core.autocrlf=true`：**提交时把 CRLF 规范化成 LF，检出时又把 LF 换成 CRLF**。两边都可能改写字节，而这个仓库的核心声明恰恰是「本仓库的代码就是产出 `results/` 那次运行的代码，指纹 `e844a6d55780dc7e`」。

**实测读数**（不是推理）：把包内容提交后，用 `core.autocrlf=true` 克隆一次——

| 情形 | 克隆出的文件中含 CRLF 的 | 与包内逐字节不一致 |
|---|---|---|
| 提交里**没有** `.gitattributes` | 56 / 57 | **49** |
| 提交里**有** `.gitattributes`（`* -text`） | 0 | **0** |

也就是说：没有这个文件，**任何 Windows 读者克隆下来算出的哈希都不等于文档里写的那个**，而代码一个字节都没被改过。读者只能得出「代码被人动过」的错误结论——正是这个项目反复强调要避免的那类「读数被口径改变」。

**我自己先踩了一遍，这是值得记下来的部分。** 第一次的顺序是：先 `git add -A`，后写 `.gitattributes`。随后克隆测试显示**仍有 7 个文件不一致**，而这 7 个恰好就是上面那张表里的 7 个。原因：`git add` 已经把这 7 个文件的**规范化后的 blob** 写进索引，而 `git add` 会因为 stat 缓存（内容看起来没变）**不重读**它们；属性是后加的，对已有索引条目不追溯生效。**顺序错了，保护就等于不存在。**

**处置**：

- 新增 `.gitattributes`，内容为 `* -text`——**所有文件都不做行尾规范化**，提交与检出都保持原字节。
- **不**选择「统一成 LF」：那样仓库里的字节就不等于算指纹时的那份字节，文档里的哈希从克隆件复算不出来。这份交付物的身份**就是**它的字节，所以宁可让仓库里行尾不统一（这是个不好看但诚实的结果）。
- 重建索引使属性对全部文件生效；`push-to-github.sh` 里加了 `git add --renormalize .`（git 为「改了 text 属性之后修正索引」提供的补救手段），并加了一道**核验**：逐个比对索引 blob 与「按当前属性重新哈希工作树文件」的结果，不一致就拒绝提交。
- **验证方式**是把仓库真克隆一遍再比字节，不是在本地 `git status` 上看一眼——本地干净和克隆一致是两件事（上表第一行就是证据）。

**代价**：仓库内行尾不统一（50 个 LF、7 个 CRLF，另有 1 个空文件）。这是为了让「逐字节相同」这句话对读者成立而接受的代价。

**这件事的教训与第 1 条同类**：一个交付件可以在所有自检里全绿，同时它的**核心声明**在传输环节被悄悄破坏。区别在于第 1 条是脱敏漏了一个值，这条是**整个指纹机制对 Windows 读者失效**——而且它不产生任何错误信息，只会让读者算出一个对不上的哈希。
