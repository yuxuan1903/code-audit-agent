**这些读数取自交付副本自身**，不是从开发目录抄来的——这是「交付的这份东西确实能跑」的唯一证据。

完整性前提：本仓库的 45 个代码文件与开发目录**逐字节相同**（`engine/` 一个字节未改），哈希见 `../文件校验清单-GitHub包.json`。因此这里的读数对两边都成立。

## 环境

| | |
|---|---|
| 解释器 | Python 3.14.5 |
| 运行方式 | `python -I <脚本>`（隔离模式） |
| 环境变量 | `PYTHONIOENCODING=utf-8`（控制台默认 GBK，中文输出会炸） |
| 被审靶子 | `ylinux_old-master`（105 个 `.py` / 11,791 行；Python 2 / Django 1.x） |

`-I` 隔离模式隐含 `-P`，即**脚本自身目录不进 `sys.path`**。所以 `tests/` 里的脚本用下面这行显式加回来：

```python
sys.path.insert(0, str(Path(__file__).resolve().parent))
```

这不是随手加的——缺了它，`from _target import require_target` 会抛 `ModuleNotFoundError`。

### ⚠️ 读这张表必须知道的两件事

**1. `_t_agent.py` 的退出码恒为 0，不能当通过证据。** 它末尾没有 `sys.exit()`。通过证据是模块级计数器 `e_bad`（604 定义 → 610 由 `echeck` 自增 → 1111 判定），末行打印的 `✅ 收敛对账四项动作齐备` 就是 `if not e_bad` 那一支——`e_bad == 0` 是直接观察到的。

**2. `❌` 的条数不是失败数。** `_t_agent.py` 的 2 项 `❌` 是**被故意拒绝**的工具调用标记：

| 标记 | 内容 | 紧随其后的断言 |
|---|---|---|
| `T4 ❌` | `record_finding` 缺必填字段被拒 | `✅ 第一次被拒、其余通过` |
| `T7 ❌` | `conclude` 被未处置候选的 blocker 拦住 | `✅ 第一次被 blocker 挡住、补完后通过` |

把它们数成失败会得到完全相反的结论：这里真正被验证的是**拒绝路径生效了**。

## 四、发布前自检

发布包的构建脚本（`_build_github_package.py`，**不在本仓库内**）做了两组检查：

| 检查 | 对象 | 结果 |
|---|---|---|
| 与源**逐字节**比对 SHA-256 | 45 个代码文件 | ✅ 全部一致（`engine/` 未改动） |
| 脱敏硬断言 | 4 个 `results/` 文件 | ✅ 六位口令原文 0、用户名 0、Windows 用户目录前缀 0、各类令牌形态 0、私钥块 0、带密码连接串 0 |
| 同一断言，范围含全部说明文件 | 11 个 `README.md` / `docs` / `results` 文件 | ⚠️ **首轮拦下 3 处**：`docs/03` 里我为了演示 `grep` 写进了靶子口令原文（真问题，已改为用模式查找），另 2 处是提及 Windows 用户目录前缀这个模式名（改散文，未放宽断言）。见 `docs/03` 第 1 条末尾 |
| **全靶子凭据字面量比对**（交付前另做） | 靶子全部 `.py` → 4 个 `results/` 文件 | ✅ 靶子上「像值而非标识符」的凭据引号字面量共 **29 个**，**没有一个**出现在发布件里 |
| 残留清单（只报告） | 4 个 `results/` 文件 | 1 条（304 字符、含空格与中文的赋式字面量——凭据不含空格，判定为散文引用） |
| **克隆件逐字节比对 + 指纹复算**（交付前另做） | 整个仓库 58 个文件 | ✅ 克隆件与包内 **0 个字节不一致**；克隆件 `code_digest` == 包内 == `e844a6d55780dc7e` |

**最后一行是这批检查里最该被复跑的一条**，因为上面几条都在**本地**验证「包是对的」，而它验证的是「**读者拿到手的那份**还是不是对的」——这两件事不一样。

做法：把仓库连 `.git` 一起复制到临时目录，在那份副本里提交（throwaway 身份，仅存活于临时目录），再用 `core.autocrlf=true` 克隆它，然后把克隆件与包内逐字节比对，并在克隆件上跑 `build_fingerprint()`。

为什么非做不可：本交付件里有 **7 个文件是 CRLF**，其中 `engine/providers/` 下 3 个**在 `code_digest` 的计算范围内**。Windows 版 Git 默认会改写行尾，**提交时和检出时都可能改**。实测——提交里没有 `.gitattributes` 时，克隆出的 57 个文件里 56 个含 CRLF、**49 个与包内不一致**；有 `* -text` 时是 0 个。机理与处置见 `docs/03` 第 8 条（包括我先把顺序做错、克隆测试才把这 7 个文件揪出来的那一段）。

> 这条检查**只在交付前跑过**，脚本不随仓库发布，所以第三方看到的是结论而不是可复跑的过程。**诚实的替代品**：读者克隆后自己跑
> ```bash
> python -I -c "import sys;sys.path.insert(0,'.');from engine.util import build_fingerprint;print(build_fingerprint()['code_digest'])"
> ```
> 输出 `e844a6d55780dc7e` 即成立。**如果输出别的值，那说明代码被改过或是传输环节改了字节——按本文档的口径，这时不能把 `results/` 里那两次运行当作当前代码的产物。**

**第 3 行的边界要说清**：它证明的是「靶子上这 29 个凭据值没有一个出现在发布件里」，**不是**「脱敏把每一个都拦下了」——报告本来就没引用到其中大多数行。让脱敏自己证明自己，正是 `docs/03` 第 1 条记下的那个错误。

硬断言刻意使用**与脱敏规则无关**的具体事实，避免用同一套正则自证。即便如此，**通过 ≠ 保证无敏感数据**：正则扫不全，这是已知边界（`engine/redact.py` 自己的注释就写着「它不保证扫全（没有任何正则能）」）。

## 五、11 条 finding 的锚点核对（交付前补做）

对 `results/fix-d` 的 11 条 finding，逐条取出 `location.file` / `line` / `end_line`，**回到靶子源码打印锚点附近原文**，判断「报告描述的行为是否真的在那一行」；对三条决定性前提另做定向核查。

| 核对项 | 结果 |
|---|---|
| 行号偏移 | **0 处**（11 条全部落在声称的位置上） |
| 锚点偏移 | **1 处**：F-009 锚在 `:134`（重定向行），破坏性调用在 `:133` |
| 区间缺陷 | **2 处**：F-007 `end_line=62 < line=134`（倒置）；F-006 `232–430` 跨 4 个函数（过宽） |
| 关键前提（另核） | ✅ F-001 链条走通（分支不转义 → `ylinux_text_filter` 不转义 → 6 个模板 `\|safe`）；✅ `AuthenticationMiddleware` 不强制登录（`app/account/middleware.py:15-19`）；✅ `MIDDLEWARE_CLASSES` 无 `CsrfViewMiddleware`（`settings.py:98-103`） |

**这条为什么重要**：`docs/03` 曾把「没有逐条核对行号」列为没做到的事，并注明行号偏移在这类工具里是常见错误（第二代原型上发生过：称 `has_auth:39-44`，实际 39-45）。核完的结论是**第一代原型这 11 条没有偏移**——但只有核过才能这么说，报告自己说没有不算证据。

逐条结论与残余不确定性见 `results/人工分析报告.md` §2–§3。
