# 设计思路

这份工具要解决的问题不是「找出可疑代码」——那部分静态引擎已经做得很好了。真正难的是：**在证据不足时不说结论。**

一个把 `bandit` 输出包装成报告的东西，会在真实靶子上产生几十条噪声，开发团队被误报拦下第三次之后就再也不看它了。所以本项目的每一条设计决策几乎都在回答同一个问题：**凭什么让一个人类读者相信这句话？** 下面九条按此展开。

---

## 一、静态引擎只给候选，不给结论

靶子上有两条 `bandit` 的 B608（SQL 注入）命中，位置在 `app/account/backends.py:43` 与 `:57`：

```python
sql = "SELECT ... WHERE %s = %%s" % (qn(model._meta.db_table), ...)
```

B608 看到的是「字符串拼接进 SQL」。而实际上，拼进去的每一段都是 `qn()` 引用的字面量标识符（表名/列名），用户输入走的是 `%s` 参数化占位符——**不是注入**。要否定这两条，必须做数据流推理：追到每个拼接项的来源，确认它是常量而非外部输入。

这种推理是本项目引入 LLM Agent 的理由。但结论并不因此就交给 Agent 自由发挥：引擎命中进入账本成为**候选**，候选必须被逐条处置——报为 finding，或被驳回**并写明理由**。

`tests/ground_truth/ylinux.json` 里 S1/S2 两条正是这个场景，用来检验「引擎误报有没有被正确驳回」而不是「有没有被无视」。实测两次运行都驳回了，理由 174 / 138 字，写明了 `qn()` 引用与参数化传值两个依据。

## 二、裁定的词表里必须有一个「我不知道」

`engine/schema.py` 的五值裁定：

| 裁定 | 含义 |
|---|---|
| `CONFIRMED` | 证据充分且独立复核通过 |
| `FALSE_POSITIVE` | 已排除 |
| `NEEDS_HUMAN` | **代码之外的事实决定结论**（如部署配置、网关是否鉴权），静态无法判定 |
| `UNVERIFIED` | 未经对抗验证 |
| `PARTIAL` | 部分成立 |

`NEEDS_HUMAN` 是刻意加的，代码注释写明：**「不要为了给结论而猜」**。鉴权是否真的生效取决于反向代理与网关配置，那不在被审代码里；静态分析能确认的只有「这个视图上没挂装饰器」。把后者说成前者，就是在编一个读者无法核实的故事。

代价是这份工具的输出**永远达不到 `CONFIRMED`**（实测两次运行的裁定分布是 `{NEEDS_HUMAN: 3, UNVERIFIED: 8}`，`CONFIRMED` 出现 0 次）。这是设计上接受的：一个只会说「我不确定」的工具仍然有用（它把「需要看哪里」说清楚了），而一个会说谎的工具只要错一次就再也没人信。

`report.py` 还会在报告里主动标注：`NEEDS_HUMAN` **不等于**已验证通过，这些条目在人工核验前不应作为决策依据。

### ⚠️ 但这个词表在本次交付里被兜底占满了

上面写的是**设计意图**。实测不是这样：两次运行的报告里 `NEEDS_HUMAN` 共出现 **5 次，5 次全部来自 `verify.py:235-239` 的兜底**——验证者没在 8 轮内提交 `submit_verdict`，引擎代替它写下 `NEEDS_HUMAN` 与固定话术（`reasoning` = 「验证者未在预算内提交结论。」，`sanitizers_checked` 为空）。**没有一次是验证者审完之后判断「这事静态定不了」。**

而 `report.py:230-233` 的摘要按裁定值计数，并断言：

> 这**不等于**已验证通过，**是验证者把判断退回给了人**。

这句在本次交付里**不成立**。要区分两种来源，只能去读逐条区块里的 `验证者推理` 字段——摘要读不出来。这是本次交付发现的一个真实缺陷，见 `docs/03-问题与取舍.md` 第 7 条；它也是「词表里有一个『我不知道』」这条设计在**实现层**必须再走一步的地方：**兜底与判断不能共用一个值**。

这不否定 `NEEDS_HUMAN` 存在的理由——若验证者没提交时把 finding 留在 `CONFIRMED`，那才是灾难。兜底的**方向**是对的，错的是它替验证者说了话。

## 三、覆盖度是契约，不是统计

七类风险（C1 注入 / C2 反序列化 / C3 认证授权 / C4 凭据配置 / C5 文件路径 / C6 依赖供应链 / C7 AI 代码特有）**每一类都必须落到一个终态**才能收口。终态是三种，且必须区分：

- `covered` —— 审了，有发现
- `no_issue` —— 审了，没有（**必须附上「怎么确认没有」的依据**）
- `not_covered` —— 没审

报告第二节把这张矩阵放在最前面，并写了一句话：

> 某个类别没出现在发现列表里，可能是「审了、没有」，也可能是「根本没审」。

静态审计报告最常见的失效方式不是「报错了」，而是**读者默认「报告没提就是没问题」**。把 `no_issue` 与 `not_covered` 分开、并要求 `no_issue` 附依据，是在对抗这个默认。

## 四、账本是一等公民：每个候选都要有出口

`engine/agent/ledger.py` 记录全部中间态——候选、finding、覆盖度、事件流。收口门禁要求：

- 七类覆盖度均已落终态；
- **全部**引擎候选已处置（报出或驳回，且驳回必须给理由）；
- 所有 HIGH/CRITICAL 已提交独立对抗验证。

「必须给理由」不是形式主义。实测拒绝路径的输出是：

```
处置候选 C0001 必须给出 reason——无理由关闭等同于静默忽略，不可审计
```

候选的**条数**因此永远不是「有效发现数」。这一点被刻意做成可检验的：`tests/_t_engines.py` 会断言「空理由处置被拒绝」「不存在的候选 id 被拒绝且回显可用 id」。

## 五、对抗验证用隔离上下文，且强制枚举净化器

`engine/agent/verify.py` 为每条需要复核的 finding 开一个**独立的 Agent 上下文**，它看不到产生该 finding 的推理过程——只拿到主张与证据，任务是**反驳它**。关键约束：

- 必须逐个枚举可能的净化点（`sanitizers_checked`），说「我看了、没有」也要留痕；
- 必须提交 `submit_verdict`，不能「跑完就算」；
- 不允许它引用前一个上下文里的结论。

隔离是必要的：同一个上下文里，模型倾向于为自己刚说过的话找补。这与「让另一个模型复核」的动机相同，但更省——复核者只需要看一条主张，不需要重跑整轮审计。

## 六、对账线索：治「提到了但没落账」

这是本项目里最贴近真实失败模式的一个机制，值得单列。

观察到的现象：模型的**推理文本里已经提到了某个位置**（比如「settings.py:18 是 DEBUG=True」），但那句话没有变成一条 finding、也没有进入候选清单，于是它对报告没有任何贡献。这是纯粹的流程漏损——不是没看见，是看见了没记。

`engine/agent/recall.py` 扫描 Agent 的推理文本，把「提到危险位置」的地方提为**对账线索**，交给模型表态。它有两个已知的真实战例：

1. `fix-d` 这次运行里，`DEBUG=True` 在推理轨迹里出现过一次，**从未变成 finding**——这正是真值 V1，被记为漏报。对账线索就是为这类漏损设计的，而它这次没能兜住（配额/时机问题，见 `docs/03`）。
2. 更早的 `real-reap` 运行里，第 37 轮推理提到了 V10 的净化点，但线索配额已在第 32 轮用尽，这条提及永远没变成线索。用掉的那 6 条配额里 5 条最终被系统自动回收——**配额烧在了「再等两轮它自己就落账了」的位置上**。

第 2 条逼出一次真实的参数实验：`tests/_tune_recall.py` 在四份已有账本上离线重放扫描器，扫描「冷静期 × 配额」网格，同时看两个指标——**捞到了吗**（真值位置有没有进入提名）与**浪费了吗**（提名的条数里有多少最终被自动回收）。只优化前者会把参数推向「提得越多越好」，而提得越多模型要处置的就越多；实测某次运行 12 条线索只处置了 1 条。**配额的价值在于被逐条看过**：提出却没人看，比不提更糟——报告会多出一段「未复核」的清单。

## 七、归因三分：内嵌库的缺陷不算项目缺陷

`collect()` 把在审文件分成 `project` / `vendored`（内嵌改造的第三方库）/ `dependency`。靶子里内嵌了 `markdown`、`django_xmlrpc`、`sessions` 等库，它们自身有已知缺陷——但把第三方库的缺陷记成「本项目漏洞」是归因错误。

- 报出不算错，**归因错了才算错**（`score.py` 对 A1/A4 两条陷阱的判定逻辑就是这样写的）；
- 边界声明也是一维评分：报告必须提及所有被归因为非项目的文件（实测 2/2）。

同时 `collect()` 还要给出**入口契约**：哪些 HTTP 路由、哪些 XML-RPC 方法可达、各自要求什么级别的鉴权。`tests/_t_collect.py` 对 22 项入口逐条断言（实测 22/22）。没有入口清单，「这个 sink 可达吗」就只能靠猜。

## 八、脱敏在生成时做，而不是在输出时做

`engine/engines/secret_runner.py` 扫到凭据后，**立刻**把值送进 `SecretVault` 换成指纹，报告里只留「前 3 字符 + `***` + 长度 + 指纹」。原值不进上下文、不进账本、不进报告。`secret_runner.py` 的注释把这条绑定写死了：

> 本引擎与 `redact.py` 是**绑定**的：命中值在离开本循环之前就被送进……

`engine/agent/registry.py` 则在**每一个工具结果**上再跑一遍 `scrub()`——因为模型可能从我们没预料到的路径上把凭据读出来（测试夹具、注释里的示例密钥）。

这个「生成时脱敏」的选择是被一次真实事故推动的，不是预设：账本里含被审代码片段与凭据字符串，曾经混进过一次交付包，文件清单从 61 条跳到 145 条。所以本项目自己的交付约定明确把**任何运行账本**排除在发布之外。本次交付沿用了这条约定。

同时它有一个**已在本次交付中暴露的漏洞**：`assigned_secret` 规则要求引号内 ≥8 字符，而靶子里的数据库口令是 6 位，于是带着原文进了报告标题。详见 `docs/03` 第 1 条——这是本次发布才发现并修掉的。

## 九、构建指纹：让「两次运行可比」成为可核事实

`engine/util.py:build_fingerprint()` 对 `engine/**/*.py` + `audit.py` 算一个 `code_digest`，写进报告。设计理由值得原文引用：

> 两次运行的 `code_digest` 不同，就**不能**把两份报告当作对照，任何「改进了/退步了」的结论都不成立。
> 只算**会产生报告的那部分代码**（`engine/` + `audit.py`），不含测试与设计文档：改了测试不该让两份报告失去可比性，而改了引擎就必须失去。

`extra_config`（预算、阈值、开关）**单独列**，不与代码合成一个哈希——「跑的是哪份代码」与「用的是哪套参数」是两个问题，合成一个就无法从指纹差异里看出到底是哪个变了。

这条设计在本次交付里立刻发挥了作用：`results/` 里两次运行的指纹是 `e844a6d55780dc7e`（fix-d）与 `a766d25a7b9c65de`（ctl-b），逐文件比对显示中间那批修复动了 **7 个文件**（`agent/loop.py`、`agent/prompts.py`、`agent/registry.py`、`config.py`、`providers/base.py`、`providers/mock.py`、`report.py`）。所以 `ctl-b` 那份 60% 召回的报告**不能**用来论证「改动让它退步了」——它们是两个不同工具的产物。没有这个指纹，这个错误结论几乎一定会被写出来。

它同时暴露了一个缺口，但**不是我最初以为的那个**：模型名其实记着——`build.config` 里有 `model: deepseek-v4-flash`，报告正文里也印了。真正的缺口是**没记「`--provider auto` 解析成了哪个端点」**：`config` 里存的是配置值 `auto`，不是解析结果；`base_url` 同样不在产物里。所以「同一个模型名、换了端点」这种变化，指纹与产物都看不出来。

（这一条是我为了写 README 的「依赖哪些模型」去查产物时先写下「模型名没记进报告」，后来真去查 JSON 才发现记着——**我自己的文档也犯了一次「没核实就下结论」**。见 `docs/03` 第 5 条。）

## 与「确认漏洞」的距离

把以上拼起来，这条流水线在靶子上确实产出了真实问题。`fix-d` 报告的 CRITICAL 一条是：

> `lib/ylinux_xmlrpc.py` 的 `delete_all_topic` / `delete_topic` 只校验认证不校验归属，任意注册用户可删除全站主题

这是真值 V9，也是这个靶子上最重要的一个缺陷。它被评为 `NEEDS_HUMAN` 而不是 `CONFIRMED`，原因是**对象级授权是否真的缺失，取决于这道接口有没有被网关或其他层拦在前面**——那不在代码里。

所以更准确的说法不是「它没找到洞」，而是**它找到了，并且诚实地说了「剩下的要靠人看」**。本项目的设计目标就是这个：把「需要人看的地方」缩小到几条，并且每条都附上可核对的证据与行号。
